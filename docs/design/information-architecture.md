# RYCODE information architecture

RYCODE has three related but intentionally different environments.

## Public website

Primary: Services, Solutions, Problems, Industries, Projects, Blog, About.

High-intent actions: Start Project, Technical Review, SEO Audit, Contact, Login.

The public environment is editorial and low-to-medium density. Navigation should explain capability before asking for a lead.

## Customer workspace

Primary: Overview, Projects, Requests, Files, Payments, Support, Notifications, Profile.

Project context: Overview, Milestones, Activity, Files, Payments, Support.

The customer workspace answers: what is happening now, what RYCODE needs from me, what happens next and whether anything is due. It must not expose internal operational detail.

## Admin operating system

Operations: Overview, Leads, Customers, Projects, Support.
Finance: Finance / Invoices.
Content: Content, Authors, Categories, Tags, FAQs, Media.
Insights: Analytics, SEO.
System: Users, Roles, Audit log, Settings.

Admin is dense and action-oriented. It should use grouped navigation and tables where records are being compared.

## Cross-link rules

- A lead can become a customer/project only through the existing server action and explicit conversion state.
- A project links to milestones, activity, files, finance and support without duplicating those records.
- CMS relationships use searchable content relationships; the UI must never ask editors to type IDs.
- Customer-facing surfaces show only records allowed by the actor scope.
- Public content links back to related services, solutions, problems and a purpose-built conversion flow.

## Route conventions

- Localized public and authenticated routes share the locale prefix generated by the app router.
- `/dashboard/*` is customer-facing; `/admin/*` is staff-only.
- Authenticated environments must never reuse the public site header as their primary navigation.
